## 1. Цель продукта

Создать настольную программу на Go для Windows 11, рассчитанную прежде всего на ASUS Zenbook DUO UX8407AA в горизонтальном положении. Программа должна открывать документ в двух синхронизированных безрамочных окнах: одно окно на левом экране, второе — на правом. Первый релиз поддерживает PDF, последующие — EPUB, FB2 и FB3.

Приложение не должно зависеть от жёстко заданных разрешения, DPI, порядка или идентификаторов дисплеев конкретной модели. Оно определяет топологию экранов через Windows API, предлагает выбрать левый и правый экран и сохраняет выбор. Это позволит работать после смены масштаба Windows, поворота устройства, переподключения экранов и на других двухмониторных системах.

## 2. Точное поведение режимов

### 2.1. Режим «Разворот» (постраничное перелистывание)

- На экранах одновременно показана пара страниц `(N, N+1)`.
- Команда «вперёд» атомарно заменяет пару на `(N+2, N+3)`.
- Команда «назад» атомарно заменяет пару на `(N-2, N-1)`.
- Для естественного разворота LTR нечётная страница по умолчанию находится справа; обложку можно показывать отдельно, оставляя левый экран пустым. Настройка «начинать разворот с первой страницы слева» отключает это правило.
- Для документов RTL порядок зеркалируется.
- Если страницы нет (начало/конец документа), соответствующий экран показывает нейтральный фон, а существующая страница остаётся на своей стороне.
- Переход должен быть синхронным: старая пара остаётся видимой, пока обе новые страницы не готовы, после чего окна обновляются в одном кадре/транзакции состояния.

### 2.2. Режим «Непрерывная прокрутка»

- Оба экрана образуют один логический двухстраничный просмотрщик, но остаются отдельными окнами.
- В устойчивом состоянии показаны текущая страница и одна соседняя: при движении вперёд — `(N, N+1)`, при движении назад — `(N-1, N)`.
- Колесо мыши, тачпад, сенсорный жест и клавиши изменяют единый `scroll position`; оба окна обновляются из одного состояния.
- Пока текущая страница уходит, соседняя плавно занимает её место, а за границей подготавливается следующая страница. В памяти разрешено держать больше двух страниц, но пользователю одновременно показываются текущая и одна соседняя.
- Переключение направления прокрутки не должно вызывать скачок позиции: якорем служат номер страницы и нормализованное смещение внутри неё.
- Масштаб и вертикальная позиция согласованы между экранами. Для страниц разного размера используется общий масштаб `fit page`/`fit width`, а свободная область центрируется.

Перед окончательной реализацией непрерывного режима сделать интерактивный UX-прототип: формулировка «текущая + следующая/предыдущая» допускает разные ожидания при переходе через границу страницы. Утвердить на реальном устройстве направление движения и момент смены «текущей» страницы.

### 2.3. Общая навигация

- Открытие файла, drag-and-drop и список недавних документов.
- Переход к странице, оглавление, история назад/вперёд, закладки.
- Масштаб: вписать страницу, вписать ширину, пользовательский процент; масштаб применяется к обоим экранам.
- Клавиатура: `←/→`, `Page Up/Page Down`, `Home/End`, `Space/Shift+Space`, `Ctrl+O`, `F11`, `Esc`.
- Мышь, тачпад и сенсорный экран; команды принимаются любым окном и поступают в единый контроллер.
- Сохранение последней страницы, режима, масштаба и позиции отдельно для каждого файла.
- При исчезновении второго дисплея — безопасный переход в одно окно; при его возвращении — предложение восстановить двухэкранный режим.

## 3. Предлагаемая архитектура

Основная идея — не связывать формат документа с окнами и навигацией.

```text
Input (keyboard / wheel / touch)
              |
              v
      Reader Controller
       |      |       |
       |      |       +-- Session/Settings Store
       |      +---------- Spread & Scroll State Machine
       v
 Document interface ---- PDF / EPUB / FB2 / FB3 adapters
       |
       v
 Render Scheduler -> memory-bounded cache -> Left/Right ViewModel
                                             |          |
                                             v          v
                                         HWND left  HWND right
```

### 3.1. Слои

1. **Windows host** — перечисляет мониторы, различает рабочую область и физические координаты, создаёт два top-level HWND, обрабатывает DPI/поворот/hot-plug/fullscreen и маршрутизирует ввод.
2. **Application/controller** — единственный владелец состояния чтения; формирует неизменяемый снимок для обоих окон и не допускает их рассинхронизации.
3. **Layout/state machine** — чистая Go-логика режимов «Разворот» и «Прокрутка». Не знает о PDF и Windows, поэтому полноценно покрывается unit-тестами.
4. **Document model** — общий интерфейс форматов: метаданные, число страниц или поток секций, размеры, оглавление, текст, ссылки и отрисовка заданной области.
5. **Render scheduler** — отменяемые задания с приоритетами: видимые страницы, ближайшая страница по направлению движения, остальной prefetch. Старый результат отбрасывается по `generation ID`.
6. **Cache** — LRU-кэш растров по ключу `(document, page, scale, rotation, color mode, crop)` с лимитом по байтам, а не по числу страниц.
7. **Persistence** — JSON или SQLite в `%LocalAppData%`; запись атомарная, без изменения исходного документа.

### 3.2. Предварительный интерфейс документа

```go
type Document interface {
    Info(ctx context.Context) (DocumentInfo, error)
    PageCount(ctx context.Context) (int, error)
    PageInfo(ctx context.Context, page int) (PageInfo, error)
    Render(ctx context.Context, req RenderRequest) (image.Image, error)
    Outline(ctx context.Context) ([]OutlineItem, error)
    Text(ctx context.Context, page int) ([]TextBlock, error)
    Close() error
}
```

Для reflowable-форматов число визуальных страниц зависит от области, шрифта и масштаба. Поэтому перед EPUB/FB2 интерфейс нужно расширить отдельным `PaginatedDocument`/`FlowDocument`, не имитируя фиксированные PDF-страницы. Результат пагинации идентифицируется ключом настроек и хранит устойчивое логическое место (spine/абзац/смещение), чтобы изменение окна не теряло позицию чтения.

### 3.3. UI и отрисовка

- Базовый вариант для исследования: тонкий Win32-host на Go + два WebView2/композиционных представления для панели управления и полотна страницы. WebView2 привязывается к родительскому HWND и умеет отдельный масштаб растеризации.
- Альтернатива для сравнения в техническом прототипе: полностью нативный Win32 + Direct2D/Direct3D. Она сложнее, но даёт лучший контроль задержки, памяти и сенсорного ввода.
- Не выбирать UI-фреймворк только по простоте окна «Hello world». Обязательный spike должен подтвердить два независимых полноэкранных окна, PMv2 DPI, ввод с обоих экранов, синхронное обновление, GPU-отрисовку большой страницы и создание подписанного установщика.
- В manifest сразу включить `PerMonitorV2`; все координаты мониторов и DPI обрабатывать явно. Не считать, что оба встроенных экрана всегда имеют одинаковый DPI.

## 4. PDF: первый рабочий формат

### 4.1. Выбор движка через короткий spike

Сравнить минимум два варианта на наборе реальных журналов и книг:

- **PDFium** — предпочтительный кандидат для распространяемого приложения с разрешительной лицензией; проверить качество/полноту Go-binding, сборку DLL, text extraction, links, password-protected PDF, отмену render-задач и ARM64/x64 при необходимости.
- **MuPDF / go-fitz** — сильный эталон по качеству и простой Go API, но MuPDF/go-fitz распространяется по AGPL либо требует коммерческой лицензии. Не включать его в продукт до письменного решения о модели распространения.

Критерии решения: качество шрифтов и изображений, ICC/CMYK, прозрачность, повреждённые файлы, большие страницы, время первой страницы, повторный render, потребление памяти, параллельность, лицензия, размер поставки и простота обновления.

### 4.2. Особенности реализации PDF

- Открывать файл только для чтения; поддержать Unicode-пути и длинные пути Windows.
- Рендерить в физическом размере конкретного экрана, с небольшим oversampling только при необходимости.
- Не разделять один небезопасный native context между goroutine: использовать документированные контексты/locks или пул независимых renderer instances.
- Отменять устаревший prefetch при быстрой навигации.
- Обрабатывать пароли отдельным диалогом; пароль не сохранять по умолчанию и не писать в лог.
- На первом этапе: просмотр, оглавление, ссылки, выделение/копирование текста и поиск. Аннотации и редактирование PDF — вне MVP.

## 5. Последующие форматы

### 5.1. EPUB

- Реализовать безопасное чтение ZIP-контейнера, `container.xml`, package/spine/navigation documents по EPUB 3.3.
- Разделить fixed-layout EPUB (ведёт себя близко к PDF) и reflowable EPUB (требует пагинации).
- HTML/CSS отображать в изолированном WebView2-контексте: scripts выключены по умолчанию, сетевые запросы запрещены, доступ к `file://` и произвольным локальным путям запрещён.
- Поддержать встроенные шрифты, SVG, вертикальное письмо и RTL; медиа/интерактивность можно отложить.
- Позицию хранить как устойчивый locator/CFI-подобный адрес, а не только номер вычисленной страницы.

### 5.2. FB2

- Потоково разобрать XML, метаданные, body/section, binary images, notes и ссылки.
- Поддержать также `.fb2.zip`: читать FB2 непосредственно из архива с ограничениями размера; при нескольких книгах внутри предложить выбор.
- Нормализовать документ во внутреннее безопасное HTML/DOM-представление и использовать тот же движок пагинации, что для reflowable EPUB.
- Ограничить глубину XML, размер вложений и общий объём распаковки; запретить внешние сущности.

### 5.3. FB3

- Реализовать OPC/ZIP-контейнер и XML-части отдельным адаптером.
- Сначала собрать корпус файлов и подтвердить совместимость на реальных книгах: формат менее распространён, поэтому нельзя проектировать поддержку только по одному примеру.
- После разбора преобразовывать контент в ту же внутреннюю модель, что FB2/EPUB; не создавать отдельный UI.

## 7. Этапы разработки

### Этап 0. Исследование и фиксация требований (1 неделя)

- Зафиксировать физическую раскладку Windows на UX8407AA в горизонтальном положении, номера экранов, DPI и поведение при повороте/сне.
- Сделать кликабельный или кодовый прототип двух режимов и проверить жесты на устройстве.
- Собрать тестовый корпус PDF: журналы, сканы, текст, разные размеры страниц, RTL, пароль, повреждённый и очень большой файл.
- Принять лицензионное решение и записать его в ADR.

**Результат:** утверждённая семантика прокрутки, таблица горячих клавиш, тестовый корпус и решение по PDF/UI-движкам.

### Этап 1. Технические прототипы (1–2 недели)

- Два HWND на выбранных мониторах, fullscreen/windowed, PMv2 DPI, hot-plug и восстановление раскладки.
- Показ разных тестовых изображений на двух экранах и единая обработка ввода.
- Benchmark PDFium и MuPDF на одинаковых страницах; измерить latency и peak memory.
- Проверить сборку чистой машины Windows 11 и отсутствие незаявленных runtime-зависимостей.

**Go/no-go:** на целевом ноутбуке обе страницы появляются синхронно, остаются чёткими при штатном DPI и интерфейс переживает сон/поворот/перезапуск Explorer.

### Этап 2. PDF MVP (3–5 недель)

- Реализовать `Document`, scheduler, LRU-кэш и PDF-adapter.
- Реализовать state machine разворота и крайние случаи документа.
- Добавить открытие файла, drag-and-drop, fit page/width, zoom, поворот, переход к странице, fullscreen.
- Сохранить/восстановить сессию и выбор экранов.
- Добавить обработку ошибок без падения всего процесса.

**Критерий готовности:** пользователь может открыть типичный PDF-журнал, читать его разворотами на двух экранах и после перезапуска продолжить с того же места.

### Этап 3. Непрерывная прокрутка и качество PDF (2–3 недели)

- Реализовать direction-aware пару страниц и непрерывный якорь.
- Добавить сенсорный pan, wheel/touchpad inertia, отмену render и адаптивный prefetch.
- Добавить outline, поиск, ссылки, выделение/копирование текста и пароль.
- Провести профилирование CPU/GPU/RAM и длительный soak-test.

**Критерий готовности:** при быстрой прокрутке нет перемешивания страниц, белых вспышек, накопления памяти или расхождения экранов.

### Этап 4. Упаковка beta (1–2 недели)

- MSIX или подписанный installer; file association для PDF — только с согласия пользователя.
- Логи с ротацией и кнопка экспорта диагностики без содержимого документов.
- Автообновление проектировать отдельно; не включать до определения канала публикации и подписи.
- Проверка чистой установки, обновления поверх версии и удаления.

### Этап 5. EPUB (3–5 недель)

- Безопасный parser/container, fixed-layout, затем reflowable pagination.
- Общая модель шрифта/темы/полей, устойчивые locators и оглавление.
- Прогнать официальный EPUB test suite и собственные визуальные тесты.

### Этап 6. FB2 и FB3 (2–4 недели)

- FB2 → внутренняя flow-модель → общий paginator.
- FB3 → внутренняя flow-модель после исследования корпуса файлов.
- Общие тесты изображений, сносок, ссылок, оглавления и восстановления позиции.

## 8. Тестирование

| `Clean Agile. Back to Basics-R.Martin(2020).epub` | EPUB | Открытие контейнера, оглавление, вёрстка и восстановление позиции после пагинации |

| `Cysin_Sharovaya-molniya.nwAUtg.554963.fb2.zip` | FB2 в ZIP, один файл | Чтение книги из архива и одинаковое поведение с несжатым FB2 |
| `Akunin_B._Istoriyarossiy7._Mir_I_Voyina.fb3` | FB3, ZIP/OPC | Разбор `body.xml`, `description.xml`, relationships и встроенных изображений |

Для каждого файла по мере готовности адаптера записывать результат открытия, найденные метаданные и оглавление, корректность первых/последних страниц, переходов вперёд/назад и восстановления сессии. Для PDF дополнительно измерять время первой пары и пиковую память; для потоковых форматов проверять сохранение логического места после смены шрифта/размера окна. Эталонные значения фиксировать после проверки в независимом просмотрщике.

Использовать `books/` для локальных интеграционных и ручных проверок. В `testdata/` держать небольшие воспроизводимые фикстуры для автоматических тестов. Корпус ещё нужно дополнить крайними случаями: PDF с паролем, повреждённые файлы, RTL, разные размеры страниц и большие документы.

### Автоматическое

- Table-driven unit-тесты переходов: 0/1/2/3/чётное/нечётное число страниц, LTR/RTL, обложка отдельно, начало и конец.
- Property-тесты: номера всегда допустимы; `next` затем `previous` возвращает исходный якорь; два view model относятся к одной generation.
- Race detector для чистой Go-части; native adapter тестировать отдельно с ThreadSanitizer/доступными средствами движка.
- Golden-image тесты рендера с допустимым perceptual threshold, а не побайтовым сравнением.
- Integration-тесты отмены, cache eviction, повреждённых/зашифрованных документов, Unicode и длинных путей.
- Security-тесты: zip bomb, path traversal, XXE, огромные изображения/страницы, скрипты и внешняя сеть в EPUB.

### На реальном устройстве

- Горизонтальное положение; смена левого/правого экранов; разные DPI/яркость/масштаб.
- Сон/пробуждение, блокировка, отключение одного экрана, изменение основного дисплея, поворот.
- Touch на каждом экране, touchpad, мышь и клавиатура; фокус не должен ломать общие команды.
- PDF 10/100/1000+ страниц, изображения высокого разрешения, 2+ часа непрерывного чтения.
- Проверка энергопотребления и отсутствия постоянного render-loop, когда изображение неподвижно.

## 9. Нефункциональные цели MVP

Значения подтвердить измерениями на UX8407AA после Этапа 1:

- первая пара типового локального PDF видна не позднее 2 секунд после открытия;
- переход к заранее подготовленной паре визуально укладывается примерно в один кадр, без белой вспышки;
- ввод начинает обрабатываться менее чем за 100 мс даже при незавершённом рендере;
- кэш имеет настраиваемый жёсткий лимит (стартовое значение 512 MiB) и освобождается после закрытия документа;
- сбой декодирования одной страницы не завершает приложение;
- приложение полностью работает офлайн; документы и телеметрия никуда не отправляются;
- поддерживаются x64 Windows 11; ARM64 добавлять только после отдельной проверки потребности и native-зависимостей.

## 10. Основные риски и меры

| Риск | Мера |
|---|---|
| Ограничения лицензии PDF-движка | Лицензионный ADR до добавления зависимости; PDFium как основной кандидат, MuPDF только при совместимой модели лицензирования |
| Рассинхронизация двух окон | Один controller, immutable snapshot с generation ID, атомарная публикация пары |
| Большое потребление RAM на 3K/HiDPI страницах | Байтовый LRU, отмена задач, mip/tiles для zoom, профилирование на реальных журналах |
| Разная топология экранов | Runtime discovery, сохранение стабильных monitor IDs, UI переназначения, fallback в одно окно |
| Сложная пагинация EPUB/FB2/FB3 | Отдельная flow-модель, устойчивые locators, один общий paginator |
| Вредоносные документы | Лимиты ресурсов, sandbox-политика WebView2, запрет сети/scripts, fuzzing parsers |
| Зависание native renderer | Таймаут/отмена, защитный recovery; при необходимости вынести renderer в отдельный процесс после MVP |

## 11. Решения, которые нельзя откладывать дальше Этапа 1

1. Точная UX-семантика непрерывной прокрутки на двух физических экранах.
2. PDFium или MuPDF и допустимая лицензия конечного продукта.
3. WebView2/composition или полностью нативный Direct2D UI.
4. Отдельная обложка и начальная сторона разворота по умолчанию.
5. Нужны ли сразу поиск/выделение текста в MVP или только в следующем релизе.
6. Канал распространения: private build, GitHub/MSIX/App Installer или Microsoft Store; нужен ли code-signing certificate.

## 12. Definition of Done для первой публичной PDF-версии

- Устанавливается и удаляется на чистой Windows 11 без среды разработки.
- Автоматически либо через понятный выбор размещает левое и правое окно на нужных экранах.
- Оба режима соответствуют разделу 2, включая начало/конец и нечётное число страниц.
- Навигация с любого экрана синхронна; DPI, sleep/resume и временная потеря дисплея не ломают сессию.
- Нет известных crash/data-loss дефектов на тестовом корпусе; исходные PDF никогда не изменяются.
- Пройдены unit, integration, race/static checks, smoke-test installer и ручная матрица UX8407AA.
- В дистрибутиве присутствуют лицензии всех зависимостей; решение по PDF-движку документировано.
- README описывает управление, ограничения и сборку; CHANGELOG и release checklist заполнены.
